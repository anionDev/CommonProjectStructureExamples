# Release notes

## Changes

### Repository

- All codeunits implement the version `3.0.0` of the CommonProjectStructure now. Their scripts were migrated from the former `TasksForCommonProjectStructure`-API of ScriptCollection to the `TFCPS`-API.
- Added `.ScriptCollection/ProductInformation.xml`, which declares the title of the product, the address of its remote-repository and the environment-variables its build requires, and `.ScriptCollection/OCIImages/ImageDefinition.csv`, which declares the images the product builds.
- Added a `Taskfile.yml`, so that building the product (`task bb`), starting and stopping the local test-services and regenerating the visual-regression-baselines (`task uvrb`) are reachable as tasks.
- Removed `GitVersion.yml`, which the current version of the CommonProjectStructure does not use anymore.
- Added `.betterleaks.toml`, so that the secret-scan of the pipeline has its configuration in the repository.
- Added `Contributing.md` and `ContributorLicenseAgreement.txt`, which describe under which conditions contributions are accepted.
- Added `Other/Resources/Support/InformationAboutSupportedVersions.csv`, which documents which versions of the product are supported.
- Added an overview-diagram of the codeunits and their dependencies (`Other/Reference/Technical/Diagrams/CodeUnits-Overview.plantuml`), which the pipeline renders to an svg-file.
- The single test-service `Other/Resources/TestServices/Database` was replaced by the two local test-services `Other/Resources/LocalTestServices/MariaDBDatabase` and `Other/Resources/LocalTestServices/PostgreSQLDatabase`, so that a codeunit can be tested against both database-types instead of only against one.
- The versions of the tools which the build downloads (JRE, OpenAPI-Generator, PlantUML) are pinned in `Other/Resources/Dependencies`, so that a build does not silently change when one of them releases a new version.
- Every codeunit has a `HowToBuild.md` in its reference-content now. In `DotNetLibraryCodeUnit` that file moved out of the `Articles`-folder to the place the structure defines for it.
- The `ReadMe.md` of the product lists the codeunits which exist, what each of them demonstrates and which of them the pipeline builds. Before it only listed the codeunits which are planned.

### Codeunits

- Added `FlutterCodeUnit` as the example for a Flutter-application: a minimal Material-Design hello-world-app, built for the `linux`- and `web`-targets (scaffolded via `flutter create --platforms=linux` and later `flutter create . --platforms web`).
- Added `MavenCodeUnit` as the example for a maven-project, `GoCodeUnit` as the example for a go-project and `RustCodeUnit` as the example for a rust-project. All three of them are commandline-applications which print a greeting, and all three of them are built, linted and tested by the pipeline including the measurement of the test-coverage. They put their testcases into the project itself and not into a sibling-project `<codeunit>Tests` like the .NET-codeunits do, because that is the layout maven, go and cargo define.
- `AngularCodeUnit` was migrated to the standalone-API of Angular: `app.module.ts` and `app-routing.module.ts` were replaced by `app.config.ts` and `app.routes.ts`. Its linting-configuration was migrated from `.eslintrc.json` to the flat configuration `eslint.config.js`.
- `AngularCodeUnit` demonstrates visual-regression-tests now. They open the pages in chromium, firefox and webkit, in the light and in the dark color-scheme, and compare a screenshot with a baseline-screenshot. It also got a `user-settings`-module and a development-proxy-configuration.
- `AngularCodeUnit` demonstrates how a frontend uses the API of a backend-codeunit of the same repository: the client in `src/app/generated` is generated from the API-specification of `DotNetWebAPICodeUnit` and is therefore not edited by hand.
- The database-access of `DotNetWebAPICodeUnit` was reworked: the database-context, the database-manager and the migrations written in C# were replaced by sql-files in `Resources/Database/<database-type>`, which are applied through an `SQLProvider`. The example thereby shows one statement per file and one migration per file for every supported database-type instead of hiding both in code.
- `Customer` moved from the database-layer of `DotNetWebAPICodeUnit` to `Model/BusinessTypes`, and the codeunit got a `CustomerController` which serves it.

### Tooling

- Added an `openspec`-configuration and the corresponding skills, commands and prompts for the supported AI-development-tools, so that the workflow of the repository is available in them.
